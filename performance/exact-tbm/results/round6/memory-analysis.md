Memory analysis for the selected ROUND6 typed-heap candidate

Status: the full 550,000 x 1,024 stress workflow completed with PASS (exit 0). It covers writes, queries, updates, rollback, bulk update and crash recovery: 73 independent TopK queries, two 549,997-row censuses (1,099,994 row checks of keys/categories/regenerated norms), six transaction point-row checks, and four SIGKILL events, including a verified kill before recovery reported ready. An 8,285-byte uncommitted tail was discarded. OOM and OOM-kill counters remained zero. See [summary](heap-stress-summary.json), [run metadata](heap-stress-run.json), and [raw telemetry](heap-stress.jsonl). This is a single-version capacity/correctness check, not an interleaved performance comparison, a formal per-request time-limit pass, or proof of a performance score. This reviewer used source inspection and existing telemetry only, without starting profiling, Go commands, tests, or benchmark workloads.

The recorded near-limit peaks are predominantly Linux file cache, not an anonymous allocation of the full vector dataset. Input vectors occupy 2,252,800,000 bytes (> 2 GiB); the database runs with memory.max=2,147,483,648, swap disabled, an index budget of 256 MiB, GOMAXPROCS=2, GOGC=20, and explicit fdatasync. The source binary is /tmp/seekdb-round6/bin/heap. Evidence is [heap-stress.jsonl](heap-stress.jsonl).

The whole-workflow kernel peak is 2,147,721,216 bytes (2,048.227 MiB), recorded in query_after_bulk_update. It is 237,568 bytes above the configured 2 GiB memory.max. Report the raw small overage; the verified claim is successful operation under a configured 2 GiB cgroup with swap disabled and no OOM, not an assertion that every counter was mathematically at or below 2 GiB. The cgroup was reused across restarts, so file-cache charges survived process death and stayed in the measured workflow.

The sampler reads memory.current, memory.stat, /proc/status, and smaps_rollup sequentially every 50 ms, and retains the record with the highest sampled current ([sampler](../../stress/main.go#L115), [period](../../stress/main.go#L150)). These fields are not an atomic snapshot, and kernel accounting also need not reconcile byte-for-byte. In particular, first-query sampled current is about 0.18 MiB above 2 GiB while the phase memory.peak FD reports 2,147,487,744 bytes. Preserve both raw measurements; do not force their totals to match or infer a materially larger allocation. The separate max_sampled_anon/file/rss fields have different timestamps and are not summed here. A sampled maximum is not proof that shorter allocation peaks were observed.

Write evidence and source attribution:

- At the write sampled peak, file=2,057,162,752 bytes, anon=28,495,872, kernel=61,333,504, and file_mapped=0. Both file_dirty and file_writeback are zero in that record. Most of the kernel subtotal is slab (61,030,688 bytes), predominantly reclaimable (60,980,808); slab is already included in kernel.
- [Log.Flush](../../../../minivectordb/internal/storage/log.go#L117) uses WriteAt, feeding the kernel page cache. [Log.Sync](../../../../minivectordb/internal/storage/log.go#L134) flushes and fdatasyncs before acknowledgment; neither path evicts file cache. Clean cache at the sampled peak is compatible with the required durability and does not mean the file is still buffered only in the process.
- The stress workload creates only a table before its 64-row INSERT batches ([driver](../../stress/main.go#L806)); it has no vector index during this write phase. [Table.rows](../../../../minivectordb/internal/engine/table.go#L28) retains primary-key-to-offset metadata. [INSERT planning](../../../../minivectordb/internal/engine/dml.go#L121) retains one statement's changes and encoded rows, with one reused vector scratch buffer; these are temporary statement allocations. They are not a copy of every committed vector.
- The log buffer has a 4 MiB flush threshold ([constant](../../../../minivectordb/internal/storage/log.go#L67)); Flush resets its length and retains its backing capacity unless it exceeds 8 MiB ([reset](../../../../minivectordb/internal/storage/log.go#L127)). A single oversized record can exceed the threshold before flush, so this is not a strict global heap cap. The current fixed-width rows are small.
- Write reports 46.503 s measured T, 2,305,736,704 write bytes, no read bytes, and no OOM/OOM-kill. memory.events.max=1619 records limit pressure/reclaim, not 1619 OOMs. The current evidence does not attribute the 2 GiB charge to Go heap.

Query evidence and retained state:

- The first 12-query phase passes all 12 independent reference checks. Its sampled peak is still file-dominated: anon=60,035,072 bytes and file=2,079,817,728, with almost all file pages mapped. Reported process RSS rises to approximately the cgroup limit because mapped file pages now appear in RSS; this is not a new anonymous copy of the table.
- [vectorTopK](../../../../minivectordb/internal/engine/topk.go#L155) builds the implicit index lazily on the first query. [Log.Prepare and Map](../../../../minivectordb/internal/storage/log.go#L176) expose flushed data, and [mapping.view](../../../../minivectordb/internal/storage/mmap_unix.go#L17) reserves a read-only MAP_SHARED mapping in 1 GiB steps. With this >2 GiB log the reservation is 3 GiB. Virtual mapped length and VmSize are not resident-memory usage; touched pages are the same file-cache pages counted above, with page-table overhead in kernel memory.
- [Index rebuilding](../../../../minivectordb/internal/engine/vecindex.go#L82) retains slot PKs, offsets and the slot map. The int8 prefilter estimate at 550,000 x 1,024 is 550,000*(64+1,024+32)+1,024*4+ceil(550,000/128)*16 = 616,072,848 bytes, well above the 256 MiB budget, so this workload deterministically disables full-table int8 codes/folded constants. This is a code consequence, not a heap-profile observation. Slots alone have a 35,200,000-byte budget estimate and fit. [catBlockFor](../../../../minivectordb/internal/engine/eqset.go#L135) cannot create category code copies without those codes.
- [derivedBytes](../../../../minivectordb/internal/engine/vecindex.go#L262) accounts for retained slice capacities and estimated map costs, including category/equality caches; [indexBudget](../../../../minivectordb/internal/engine/db.go#L25) aggregates other tables' indexes. It does not budget the authoritative Table.rows map, transaction overlays, query/statement/rebuild scratch, GC garbage awaiting collection, file cache, or kernel memory. Map costs remain estimates, not measurements. [Post-growth checks](../../../../minivectordb/internal/engine/vecindex.go#L183) can drop optional state after an allocation; this is not a guarantee against transient overshoot.
- Rebuild sorts a temporary [rowRef slice](../../../../minivectordb/internal/engine/vecindex.go#L113), with a 16*N-byte payload (8.39 MiB for 550,000 rows). This is temporary construction memory, distinct from retained index slots. [eqSlots](../../../../minivectordb/internal/engine/eqset.go#L51) may retain an additional exactly sized 4*N-byte slot array and owned category keys/groups, subject to the same derived budget. Neither copies the original float32 vectors.
- First-query T=71.560 s and device read bytes=7,034,777,600 demonstrate that the phase is not purely a resident CPU scan. The cumulative file-refault counter in its peak sample is 1,319,879; the preceding write sample was zero. This supports file-cache pressure, without pretending this single phase is an interleaved performance comparison or attributing all elapsed time to IO.
- Typed-heap changes affect bounded TopK admission and output sorting ([heap](../../../../minivectordb/internal/engine/topk.go#L52), [result](../../../../minivectordb/internal/engine/topk.go#L124)), not N*dim stored vectors or page-cache policy. A lower allocation count does not by itself promise a lower memory.peak once file cache fills the cgroup.

Update/recovery allocation sources identified in code and supported by the completed workflow:

- [match](../../../../minivectordb/internal/engine/dml.go#L198) builds PK and offset arrays for the matched rows. Their logical payload is 16*N bytes together, with append capacity/old arrays potentially increasing temporary allocation. [execUpdate](../../../../minivectordb/internal/engine/dml.go#L274) chooses streaming above the 8 MiB planned-payload threshold, so the completed all-row category update takes this streaming path rather than retaining all replacement vectors in chs.
- [streamUpdate](../../../../minivectordb/internal/engine/dml.go#L314) sorts pre-statement offsets, validates expressions in one pass, then writes another pass with a reused encoded-row buffer. [Table.decode/col](../../../../minivectordb/internal/engine/table.go#L114) still allocates one decoded vector/row at a time: cumulative allocation can exceed dataset size, but this does not mean all those vectors stay live together. Matching offsets and the transaction overlay remain proportional to the affected row count.
- [Txn.overlay](../../../../minivectordb/internal/engine/txn.go#L14) retains PK-to-new-log-offset metadata until commit/rollback; [apply](../../../../minivectordb/internal/engine/txn.go#L87) appends complete replacement records to the log. [commitTxn](../../../../minivectordb/internal/engine/txn.go#L119) writes COMMIT and Sync before merging authoritative offsets. Consequently bulk update can raise file-cache traffic and retain O(changed rows) metadata without retaining O(rows*dim) vector payloads. Old and new log versions coexist until compaction.
- [Recovery](../../../../minivectordb/internal/engine/db.go#L103) scans sequentially and stores only pending operation metadata until a COMMIT. On linux/amd64 each pend has a 24-byte payload; the slice grows to the largest transaction and keeps that capacity for the rest of this recovery call. Old backing arrays can await GC during growth. [Scanner.fill](../../../../minivectordb/internal/storage/scan.go#L37) normally reuses a 1 MiB buffer, increasing it for an individual larger record; payloads alias that buffer rather than accumulating full row data. Table.rows remains the authoritative retained map.
- This stress has no CREATE VECTOR INDEX. Its implicit index is not persisted: recovery reconstructs Table.rows, while [Open's rebuild loop](../../../../minivectordb/internal/engine/db.go#L90) rebuilds only indexes restored from DDL. The next vector query recreates the implicit index. Avoid attributing that later construction cost to recovery-before-ready.
- [maybeCompact](../../../../minivectordb/internal/engine/compact.go#L21) is conditional on dead-log bytes exceeding both 256 MiB and live bytes. If triggered, it temporarily keeps old/new row maps ([newRows](../../../../minivectordb/internal/engine/compact.go#L62)) and reads/writes old/new files before swapping them. This conditional source was not triggered by the completed bulk-recovery fixture: at 549,997 rows, its fixed-width live-byte lower bound is 549,997*4,126 = 2,269,287,622 bytes, while final log size is 4,313,968,692; the 2,044,681,070-byte garbage upper bound is smaller than liveLower, so the early return applies. Bulk recovery also reports zero device writes. The log source and new target can both contribute page-cache charge without being two anonymous vector copies.
- Invalidating derived sets [drops references](../../../../minivectordb/internal/engine/vecindex.go#L255); it does not synchronously reclaim Go heap pages or evict file cache. The program's [60% Go memory limit and tighter GC target](../../../../minivectordb/cmd/minivectordb/main.go#L38) do not impose a page-cache cap.

Completed bulk/recovery evidence and its limits:


- The all-row category update matched 549,997 rows and completed in 26.274 s, with 2,468,040,704 device read bytes and 2,043,359,232 write bytes. Its selected total-memory peak sample has anon=108,404,736 bytes (103.383 MiB) and file=2,029,899,776 bytes (1935.863 MiB). The phase's independently selected max_sampled_anon is 249,417,728 bytes (237.863 MiB); that maximum was not observed at the same time as the selected total-memory peak. The latter two figures must not replace or be added to each other. This is consistent with bounded vector-payload working memory plus O(N) offsets/overlay metadata; telemetry does not identify the exact object-level or live-heap composition.
- Completed recovery-before-ready phases took 0.799 s after acknowledged-commit kill, 0.682 s after the interrupted recovery/uncommitted tail, and 2.242 s after the bulk commit. Their selected peak samples all have file_mapped=0 and are dominated by charged file cache, while process RSS is only tens of MiB. Bulk recovery's independent max_sampled_anon is 47,374,336 bytes (45.180 MiB); the selected total-memory peak sample has only 22,224,896 anon bytes. This supports the sequential scanner/metadata reconstruction described above, and does not imply that the dataset was loaded as anonymous vectors. These restarts reused existing file cache; their timings are not claimed as cold-recovery comparisons.
- kill_during_recovery lasted about 11.8 ms, shorter than the 50 ms sampling period. Its selected record has anon=0 and lacks process RSS after exit, even though the kernel phase peak is higher than its sampled current. It proves neither zero allocation during recovery nor complete capture of transient peaks. The driver separately verifies the process was killed before ready, without an internal progress hook.
- The two post-bulk 12-query phases each pass their independent truth checks, and read 45,207,199,744 and 44,005,351,424 device bytes. The final log is 4,313,968,692 bytes, which requires a 5 GiB virtual mapping under the existing 1 GiB-step policy when queried. The logged page-cache pressure and read traffic are material T/B constraints; a smaller metadata allocation cannot be translated directly into a better score. These are observations of one run, without invented phase weights or a comparison E.
- The largest independently sampled anon maximum anywhere in this workflow is 263,614,464 bytes (251.402 MiB), during census #1, not at the whole-workflow total-memory peak. [The census](../../stress/main.go#L510) returns every row's id, category and scalar norm in one response. [SELECT materialization](../../../../minivectordb/internal/engine/select.go#L162) allocates all output row/value slices; [Encoder.Result](../../../../minivectordb/internal/proto/encode.go#L121) appends the full JSON response and retains its buffer capacity. Output objects are temporary; the encoder buffer is retained between requests, and garbage/Go pages need not disappear immediately. This is a concrete additional anonymous-memory source, not retained copies of every vector. No heap profile was taken, so it is not an exact allocation attribution and anon is not synonymous with live Go heap.
- Final memory.events.max=580,844 is cumulative pressure at the cgroup limit; OOM, OOM-group-kill and OOM-kill are all zero. The selected peak of query_after_bulk_recovery demonstrates the accounting distinction especially clearly: about 1,989 MiB of cgroup file cache coexist with about 306 MiB of process RSS at that sample, because much of the charged cache is not mapped into that process at that instant. The independent phase RSS maximum is a different sample and must not be substituted into this breakdown.

Budget-policy implication for the next candidate:

The existing 256 MiB budget provably disables the full 550,000 x 1,024 int8 code/parameter state, which needs a 616,072,848-byte (587.533 MiB) initial budget estimate before optional equality/category copies. Merely setting MVDB_INDEX_MEM_MB=768 or --index-mem-mb=768 cannot enable it under the existing detected 2 GiB limit: [main.go](../../../../minivectordb/cmd/minivectordb/main.go#L38) caps the requested budget at lim/4 = 536,870,912 bytes (512 MiB), still below that estimate. Any proposal to activate more prefilter data must account for this cap, the aggregate retained-capacity checks, temporary build allocations, and the page cache displaced by extra anonymous state. It requires a separately validated policy or representation change and an interleaved T/B/M comparison; no such improvement is established by this observational report.

The completed capacity/durability test supports exact operation on more than 2 GiB of vector data under the configured 2 GiB cgroup. It does not show a 2 GiB Go heap, a formal latency-limit pass, or a score improvement. Keep phase memory.peak, the selected total-memory sample, and independently sampled component maxima distinct, and do not add RSS, mmap length, file cache, estimates, or unrelated maxima into a purported peak.
