源码解释与这些观测一致：af116 的 `execUpdate` 先为所有匹配行构造完整编码副本，`chs` 持有各行切片；`enc` 扩容后，旧 backing array 仍被前面的切片引用，不能随新数组分配一起释放。因此，修改一个分类字段也会保留整条向量行的副本，扩容过程中还保留多代数组。该阶段没有物理写 I/O，符合仍停留在写入前的整批变更规划阶段。Go 的 `GOMEMLIMIT` 是软限制，不能强制释放这些仍被引用的数据。当前代码增加的大 UPDATE 两遍执行路径先验证全部赋值，再按旧日志偏移顺序逐行编码和写入，最后一次提交；其实际 T/B/M 和崩溃恢复结果需要由最终验证记录给出，不能由源码推断收益。

`memory.peak` 接近 2GiB 本身并不代表 Go 堆达到 2GiB：写入的最高 current 采样点中，anon 为 29,040,640 B、file 为 2,056,933,376 B、kernel 为 61,386,752 B。kernel 中 slab 为 61,085,456 B，其中 61,035,776 B 可回收。这里主要是文件缓存及可回收内核对象，不能把这些计入引擎的常驻向量副本；记录没有各 slab cache 的分类，不能进一步断言由某一种内核对象造成。kernel 已包含 slab 等子项，不能重复相加。失败 UPDATE 的最高 current 采样点则为 anon 1,726,439,424 B、file 407,511,040 B、kernel 13,377,536 B，其中页表 7,974,912 B、slab 5,274,840 B；这说明内核/slab 不是该次 OOM 的主要占用。它也不是 anon 峰值发生的同一时刻。mmap 按 1GiB 步长扩展的是虚拟地址范围，不等于每次额外分配 1GiB 物理内存。

本规模下，默认 256MiB 派生索引预算不足以容纳全部量化码和参数，会回退为读取日志向量的 exact 扫描。文件页缓存因此仍是后续瓶颈：首组 12 条查询产生 7,731,920,896 B 物理读取；第一次提交后恢复产生 88,540,131,328 B 物理读取。旧 `maybeCompact` 在顺序回放之后还按 map 随机顺序读取所有存活行头，即使日志不满足压缩条件也会执行。工作集超过可用缓存时，这类随机读取与页回收可能放大 I/O；记录中的 refault、缺页和读取字节数支持继续调查这一方向，但不足以将全部耗时或 I/O 唯一归因于某一函数。当前加入的存活字节下界早退优化，需要以相同驱动、相同缓存条件的交错恢复对照确认；也应继续量化查询的顺序访问、预读和缓存回收，不能只根据扫描内核耗时评价。

初版驱动存在两项已识别的验证口径问题。其一，未提交事务只有一次更新、一次删除和一次插入，约 8KiB，低于日志 4MiB 的自动 Flush 阈值；紧接着 SIGKILL 时，这些记录可能仍完全留在用户态缓冲中。因此，初版的“带未提交事务崩溃”不能证明磁盘上未提交尾部被正确丢弃。其二，启动/恢复 T 在 `cmd.Start` 和首次采样之后才开始，遗漏了启动开始的一小段工作。初版数字保留用于问题诊断，不与最终候选直接进行严格性能比较。

本轮最终验证使用的 [stress 驱动](stress/main.go) 已补上这两项：在未提交事务内执行有独立真值的 TopK 查询使记录 Flush 到文件，并断言文件长度确实超过最后提交边界；恢复后检查截断长度和相关行状态。启动前即记录时间、I/O 起点并重置 memory.peak，另外显式指定 fdatasync、256MiB 索引预算和 GOGC=20，并校验注入的退出信号确为 SIGKILL。这些是本地验证驱动的修正，未涉及正式提测。最终结论应引用修正驱动产生的结果，并将正确性压力验证与交错 T/B/M 性能对照分别说明。

修正后的 [最终压力记录](results/round3/stress-final.jsonl) 已完成：73 条 TopK 真值校验、两次各 549,997 行 census、四次强杀恢复均通过，`oom=0`、`oom_kill=0`。同规模全表 UPDATE 完成于 3.921983s，采样 anon 最高 229.402MiB；这验证了容量问题得到解决，失败与成功运行之间不计算完成时间加速比。最后一次通用排序 census 则花费 585.699s、读取 782.614GiB，说明更新后大日志仍有严重 I/O 放大；`scanSorted` 按 map 顺序访问行头是下一轮应单独定位和对照的路径。详细结果、生命周期差异和独立性能对照见 [ROUND3.md](ROUND3.md)。
